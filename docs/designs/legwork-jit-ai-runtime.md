# Design: Legwork — README-to-MCP-Wrapper Synthesizer (v1 of the Autonomous JIT AI Runtime)

Generated by /office-hours (via /plan-ceo-review) on 2026-09-22
Branch: main
Repo: drafted here in AwesomeAI/docs/designs/; implementation ships in a new
standalone repo at github.com/AwesomeAI/legwork once org AwesomeAI exists
Status: APPROVED
Mode: Builder

## Problem Statement

Developers waste real engineering time gluing together new AI repos: every time
a tool trends on GitHub, someone has to manually read the README, download
heavy libraries, fix broken dependencies (PyTorch/CUDA conflicts), and write
custom glue code before they can actually use it.

## What Makes This Cool

Point it at a repo that trended on GitHub *this morning* — zero manual
registration, never seen before — and watch it autonomously read the README,
write a working MCP wrapper, run it in an isolated sandbox, retry on failure,
and hand back a working tool. That live, unscripted run is the entire pitch.

## Constraints

- 100% open source; the only cost to a user is their own LLM/API usage
- Runs locally; no mandatory SaaS backend for the core loop
- Lightweight — v1 must not require always-on infrastructure to operate
- Security risk must be named and flagged, not hidden or hand-waved away
- License/derivative-work risk must also be named and flagged: synthesized
  wrappers are derived from third-party repos and, under the caching
  decision below, get redistributed publicly — that's a distinct risk from
  security and needs its own disclosure step, not a footnote under it
- Target wrapper language for v1: Python — the ecosystem where the
  motivating pain (PyTorch/CUDA glue code) actually lives, and where most
  trending AI repos already ship. Revisitable at eng review, not a v1 blocker.
- LLM calling convention: the codegen step targets an OpenAI-compatible
  chat-completions endpoint URL — the developer brings their own key/model
  and endpoint (direct OpenAI, or a proxy like LiteLLM if they want another
  provider). Legwork does not bundle a multi-provider shim in v1 (see
  Decided section). Consistent with "only cost is your own LLM/API usage."

## Premises

(Landscape research: OpenAPI-to-MCP code generators, auto-generate-MCP-from-docs
tools, MCP gateway/registries with live semantic tool discovery, and mature
sandboxed agent runtimes — E2B, Modal, Daytona, Firecracker microVMs — all
ship as real products already. MCP itself is the de facto standard, ~97M
monthly SDK downloads as of March 2026.)

1. The pain point (manual glue code, dependency hell) is real. — agreed
2. The genuinely novel part isn't "an MCP wrapper," "a sandbox," or "a
   registry" (all exist) — it's synthesizing a working wrapper fully
   autonomously from an **unstructured README** (not a spec), with **zero
   manual registration**, specifically for freshly-trending/uncatalogued
   repos. Existing tools need a structured OpenAPI spec or a manually
   submitted registry entry. — agreed
3. "Zero cost except LLM calls" only holds if the trending-repo index is
   static/community-curated (e.g. a JSON file refreshed by CI) rather than a
   live scraping service, which needs hosting. — agreed
4. Auto-executing an LLM-synthesized wrapper around a stranger's GitHub repo
   is a real security problem — a malicious README can prompt-inject the
   codegen step itself, before the sandbox ever runs. — agreed
5. "Ephemeral and lightweight" can't both be true for heavy ML repos — a
   Stable-Diffusion-class tool needs GBs of weights and a real GPU on first
   run; the sandbox buys dependency isolation, not speed or size. — agreed

## Cross-Model Perspective

Independent Claude subagent cold read (Codex unavailable, no conversation
bias, structured summary only):

- **Coolest version not considered:** a shared, versioned, cached wrapper
  store — synthesize once per repo-version, verify with an auto-generated
  smoke test, cache publicly — instead of per-user ephemeral regeneration.
  Resolves premise #3 (cost) and #4 (security) at once: the dangerous codegen
  step runs once, in a controlled environment, and gets audited before anyone
  else trusts the output.
- **The tell:** "highest starred GitHub repo in this era" is a status goal,
  not a technical one — it pulls toward maximalist, unscoped builds instead
  of the narrow wedge premise #2 already identified.
- **50% tool:** `mcp-gateway-registry` covers steps 1-2 (dynamic semantic
  tool discovery + routing) off the shelf; pair with E2B/Daytona for step 3.
  That's the *easy* ~70% of the pipeline by step count. The hard 50%, by
  actual difficulty, is entirely step 4 — nothing in the landscape does
  spec-free synthesis from unstructured prose.
- **One-weekend build:** only the README→wrapper synthesizer with a
  self-correcting retry loop (attempt → fail → feed stack trace back → retry).
  Registry = a hand-picked static JSON list of 3-5 repos, not scraped.
  Sandbox = a plain venv/container run manually, not orchestrated. Cut:
  routing, live scraping, ephemeral lifecycle management, injection defense
  (flag as known unsolved risk), any stars-farming scaffolding. The proof:
  an unrehearsed run against a repo that trended that same morning.

**Recommendation (subagent):** build only the synthesizer+retry-loop first —
it's the one piece confirmed novel by premise #2, fully demoable alone, and
can't be replaced by wiring together existing OSS this weekend.

**Decision made from this:** wrapper caching should be public/versioned/shared
from day one (not pure ephemeral regeneration) — the repo itself becomes the
cache, so this needs zero extra hosting infrastructure.

**Correction (from Outside Voice review):** caching does NOT resolve premise
#4 (security), and the phrase above overstated it. The automated smoke test
only proves "the tool call executed without raising" — it says nothing about
whether a wrapper quietly does something malicious. A wrapper that clears
that low bar now gets **redistributed to every future user who trusts the
cache instead of resynthesizing** — the reuse Success Criteria explicitly
wants. That converts a single-victim risk into a supply-chain distribution
risk. This is a known, disclosed limitation of the automated-smoke-test-only
model (see Decided section's injection-defense entry, corrected below), not
a resolved problem. Caching still resolves premise #3 (cost) cleanly — that
part of the original claim stands.

**Scope note:** this goes slightly beyond the subagent's raw one-weekend
recommendation, which cut all orchestration. The gap is narrow on purpose:
GitHub Actions running a smoke test against a static, hand-picked list is
automation on top of a list someone still edits by hand, not a hosted
scraping/routing service — it doesn't reintroduce the "live infrastructure"
cost premise #3 rules out. The subagent's recommendation is cited as the
reason to cut the *pipeline* (router, live scraping, orchestrated sandbox),
not as literal justification for every detail of the cache.

## Approaches Considered

### Approach A: Weekend Wedge (minimal viable — CHOSEN for v1)
Only the README→MCP-wrapper synthesizer with a self-correcting retry loop
(repo URL in, wrapper out, retries on stack trace), backed by a public
wrapper cache implemented as a folder of verified wrappers in the repo
itself. No scraper, no router, no full orchestration platform — but the
sandbox itself must be container-based (or equivalent OS-level isolation),
not a plain subprocess/venv: a venv only isolates Python packages, not
filesystem or network access, and can't enforce the Decided section's
phase-based network cutoff (see below). The likely v1 shape is two
sequential container runs sharing an installed environment — one with
network access for dependency install, one without for entrypoint
invocation — with the exact mechanics left to eng review. Effort: S.
Risk: Low. Completeness: 4/10 of the full vision — the 4/10 that's
actually hard and actually novel.

### Approach B: Full JIT Pipeline (ideal architecture — ROADMAP, not v1)
All 4 original steps built together: CI-refreshed static/curated trending
index, semantic intent router (mcp-gateway-registry patterns), real
ephemeral sandbox orchestration (E2B/Daytona-class isolation — note
`kindling-mcp` is close prior art here, Firecracker microVMs spinning up
existing OSS MCP servers), and the synthesizer+cache from A integrated from
day one. Effort: XL. Risk: High — registry freshness, routing accuracy,
sandbox hardening, and synthesis all have to work together before any demo
lands, and premises #4/#5 have to be solved for the whole pipeline, not one
piece. Completeness: 10/10.

### Approach C: Registry-First, Synthesis-Second (creative/lateral — rejected)
Ship a curated "awesome-list-as-JSON" with PR-based human-reviewed wrappers
first; add the autonomous synthesizer later as a bot that proposes PRs rather
than auto-executing code. Lower security risk for v1 (nothing auto-executes
unreviewed), builds a contributor/star flywheel early. Rejected for v1
because it's slower to the unscripted "autonomous, zero-registration" demo
that is the actual differentiator, and risks reading as "yet another
awesome-list" if the automation lags the curation.

## Recommended Approach

**Approach A now, Approach B is the roadmap destination — not a scope cut.**
Confirmed explicitly with the user: picking A sequences the work (prove the
hard, novel piece first, ship a real demo) rather than reducing the eventual
scope. The wrapper-caching decision (public, versioned, cached in-repo) is
baked into A from the start so it doesn't need to be retrofitted when B's
additional layers (scraper, router, hardened sandbox) get built on top later.

## Decided (moved out of Open Questions so Next Steps isn't blocked)

- **Retry-loop bound:** fixed at 3 attempts for v1 (not configurable — no
  flag/env/config surface in v1). Then stop and report a clear failure
  rather than loop forever. Revisitable at eng review.
- **"Verified" for v1 cache entry:** automated smoke test only, and only
  that — run in CI, matching the minimal-build spirit above. Minimal pass
  criteria: the synthesized wrapper's MCP tool call executes against the
  fixture's sample input and returns without raising. Human review
  (Approach C's model) is explicitly deferred, not folded in, and there is
  no separate "manually verified" tier in v1 — a repo whose wrapper can't
  pass the automated smoke test simply doesn't enter the v1 cache. Any
  human-review or alternate-verification tier is Approach B/C's problem.
- **Entrypoint (as used in Success Criteria):** the file or command the
  target repo's own README/docs identify as how to run it — e.g. a script
  path (`python demo.py`), a CLI invocation, or a `Dockerfile`/`CMD`. The
  synthesizer's first job is locating this from the README's stated install/
  run instructions before it can write a wrapper around it.
  **Named gap (Outside Voice review):** locating the entrypoint is NOT the
  same problem as inferring a correctly-typed MCP tool schema (named
  parameters, input/output types) from that entrypoint — the harder, more
  novel half of premise #2 that this doc had not actually specified. The
  validation spike below exists specifically to find out how that inference
  step behaves on real READMEs before more architecture is built around it.
- **Prompt-injection defense is NOT deferred to Approach B — it's a known,
  unmitigated risk that v1 ships with and discloses.** v1 auto-executes
  LLM-synthesized code against untrusted READMEs from day one, so the risk
  is incurred at v1, not later. Minimal v1 mitigation, split into two
  phases so it doesn't break the dependency-install step the whole loop
  depends on: (1) **dependency-resolution phase** — network access allowed
  (needed for `pip install`, downloading small fixture assets), but still
  scoped to the sandbox's own working directory, no access to the host or
  to unrelated paths; (2) **entrypoint-invocation phase** — network access
  cut once dependencies are installed and the wrapper actually runs. This
  doesn't stop a poisoned README from producing a bad wrapper, but it
  bounds what that wrapper can do once it's actually executing.
  **Correction (Outside Voice review):** phase 1 — network-open dependency
  install (`pip install`, arbitrary `setup.py`/install scripts) — is the
  **primary named attack surface**, not a secondary footnote to codegen
  injection. Malicious PyPI packages exfiltrating env vars or sandbox
  contents during install are a live, common real-world supply-chain
  pattern; a malicious README steering the codegen step is the second risk,
  not the main one. Both are disclosed plainly in the README, matching the
  Constraints requirement to name risk rather than hide it — but install-
  time gets named first and clearly. A fuller defense (e.g. sandboxing the
  codegen LLM call itself, static analysis of the generated wrapper before
  first run, a vetted-package-only dependency policy) is real, separate
  design work for Approach B, not solved here.
- **Pre-execution static obfuscation scan (validation spike finding,
  2026-09-22 — closes a real gap, not deferred).** The phase-based cutoff
  above protects the *execution* phases, but the spike found a real
  malicious payload that fired at **import time** — before either phase
  applies — via XOR-encoded string literals decoded and `exec()`'d into
  the module namespace on module load. Before the sandbox spins up at all,
  the fetched source (the full clone, not just the entrypoint file — see
  "Clone timing" below) gets a static scan.
  **Heuristic scope, corrected at eng review (2026-09-22):** the actual
  malicious file contains **no literal `exec(` or `eval(` token anywhere**
  — the call is resolved via `getattr(module, xor_decoded_string)` where
  `module` itself comes from `__import__(xor_decoded_string)`, specifically
  to evade a naive exec()/eval() grep. A scanner scoped to literal
  exec()/eval() calls would have MISSED this exact, already-confirmed
  file. The scan therefore also flags: `__import__()` called with a
  non-literal/computed argument; `getattr()` called with a
  non-literal/computed attribute-name argument (especially stacked with
  the above — this is the specific pattern that evaded the narrow
  version); large int/byte-array literals combined with XOR or modular
  arithmetic (a string-deobfuscation signature); and generally low
  identifier readability (single/double-character names throughout a
  file). Not foolproof — a sufficiently determined attacker can still
  evade static heuristics — but this broadened scope is what actually
  would have caught the real case this spike found, not just the narrower
  version's two function names. A repo that trips the scan gets
  `ObfuscatedPayloadDetectedError` and is refused before install or invoke
  ever run.
  **Implementation-time finding (T10, 2026-09-22):** even the broadened
  scope doesn't catch every shape of this technique — the real file wraps
  `getattr` in a lambda alias, so the "stacked" pattern's lexical-adjacency
  check misses it specifically. It's still blocked, via two weaker signals
  co-occurring rather than the one strong pattern built for it. Full
  data-flow tracking would close that specific gap; deferred to Approach B
  as a named limitation, not fixed silently by overclaiming coverage here.
  **Clone timing (eng review, 2026-09-22):** the scanner needs the full
  cloned repository tree, not just the README (which is fetched separately
  and lightly, via API). The pipeline clones the repo right after the
  reachability check — before README parsing, which now reads from the
  clone instead of a separate API call — specifically so the scan (and
  README parsing) both have the real source tree available. This is
  slightly heavier than an API-only README fetch for repos that fail
  early, but the scan has no way to run without the clone existing first.
- **LLM shim ownership:** Legwork does not bundle a compatibility shim in
  v1. It expects the user to point it at an OpenAI-compatible chat-
  completions endpoint URL (their own key, their own provider — direct
  OpenAI, or a proxy like LiteLLM if they want to use Anthropic/another
  provider that way). Bundling a first-class multi-provider shim is a
  fair Approach B/eng-review question, not a v1 commitment.
- **Execution timeout: fixed at 60s per attempt for the invoke phase** (locked
  at eng review, 2026-09-22 — not configurable, consistent with the retry
  bound's deliberately small v1 surface). A timeout counts as a
  wrapper-repair attempt (same bucket as `WrapperRuntimeError`) since a hang
  is itself a signal the generated wrapper is broken. 60s covers the
  dependency-light CPU-only fixtures v1 actually targets — heavier installs
  would need more, but v1 explicitly excludes GPU-heavy repos, so this
  matches the real v1 population, not the full ambition.
  **Resolved (Outside Voice, eng-review pass 2, 2026-09-22):** install
  phase gets its own **120s timeout** (pip installs need more room than
  invocation) and the whole run gets a **10-minute total-wall-clock
  ceiling** covering all 3 attempts plus their nested LLM infra-retries —
  the hard backstop that kills a run outright if something loops in a way
  no other timeout catches. Makes the CI free-tier-runner assumption in
  Distribution Plan actually true instead of assumed.
  **Retry prompt content (Outside Voice, eng-review pass 2):** each retry
  attempt's prompt includes the (capped) README plus only the immediately
  prior attempt's failure — never a growing transcript of all attempts.
  Keeps per-call cost roughly constant across all 3 attempts instead of
  growing, which is what the "small, predictable cost" claim in Constraints
  actually needs to be true.
- **Contributing a wrapper to the public cache in v1 is a manual step, not
  an auto-PR bot.** The CLI writes the wrapper + manifest to a local
  output directory; the user opens the PR themselves. An auto-PR bot
  (Approach C's model) is explicitly future work, not v1.

## CEO Review Findings (architecture, error-handling, security, observability)

Six gaps surfaced reviewing the above against HOLD SCOPE rigor — each decided
individually, all folded into v1 scope (none of these expand beyond Approach A,
they make it correctly built):

1. **Bad repo URL is a distinct failure from a bad README.** Before any README
   parsing, verify the repo is reachable and public. On 404/403/invalid URL,
   fail immediately with `RepoNotFoundError`/`RepoAccessError` and a clear
   message — do not burn any of the 3 wrapper-repair attempts on a repo that
   will never work.
2. **LLM infrastructure failures get their own retry policy, separate from
   the 3-attempt wrapper-repair budget.** Timeout/rate-limit get a short
   backoff-and-retry (e.g. 2 attempts, exponential backoff) that does NOT
   count against the 3 wrapper attempts. Auth failure (bad/missing key) fails
   immediately — retrying a bad key wastes time and API calls for nothing.
3. **README/repo content sent to the LLM is size-capped at 50KB** (locked at
   eng review, 2026-09-22 — covers the vast majority of real project READMEs
   while bounding worst-case token cost per attempt to a predictable amount).
   **Truncation is section-aware, not a flat byte cut (validation spike
   finding, 2026-09-22):** before cutting, look for headings like "Quick
   Start," "Usage," "Installation" (case-insensitive, common variants) and
   prioritize keeping those sections intact, cutting boilerplate (badges,
   long feature lists, changelogs) first. The spike found a flat cut can
   retain the wrong section entirely — e.g. an HTTP-service-backed install
   path when a simpler, self-contained alternative was mentioned later in
   the same README. If truncation likely caused a synthesis failure, say
   so in the failure message. Bounds worst-case cost
   per LLM call — matters directly for a tool whose pitch is "the only cost
   is your own LLM usage, and it's small." **Does NOT by itself bound total
   cost across a 3-attempt run** — see the new "Retry prompt content" entry
   below (Outside Voice, eng-review pass) for the cumulative-cost gap this
   left open.
4. **API key sourcing is env-var only, with an explicit scrub before any
   public write.** Never a CLI flag (shell history) or config file (accidental
   commit). Before writing the cache manifest or any log line destined for
   the public cache/PR, scrub for anything matching the key's format. Closes
   the most likely accidental-leak path into a public, shared artifact.
5. **Every retry attempt logs its own structured outcome, not just the final
   result.** Each of the 3 attempts records: what changed from the prior
   attempt, the exact failure class, and whether it retried or stopped. On
   final failure, print all attempts' summaries together. Makes the retry
   loop's self-correction — the actual novel, hard part per premise #2 —
   visible and debuggable instead of a black box.
6. **A bad/gamed cache entry is reverted with a plain `git revert` on its
   manifest + wrapper files.** No special invalidation tooling — the cache is
   just files in the repo (per the earlier caching decision), so this is
   already true; stating it as explicit policy here prevents a future
   contributor from building unnecessary infrastructure to solve an
   already-solved problem.

## Success Criteria

- Legwork can point at an arbitrary trending GitHub repo it has never seen,
  given only a README + entrypoint, and produce a working MCP wrapper with
  zero manual registration.
- **Reframed (Outside Voice, eng-review pass 2):** the retry loop does not
  regress on the smoke-test fixture set (a legitimate use of a small fixed
  set — a regression gate, not a generalization claim). The actual claim
  that retrying improves success rate over single-shot gets measured
  properly during the validation spike (Next Steps #0) against its larger,
  more representative sample — not against these same 3-5 fixtures, which
  Success Criteria's own next bullet already says can't prove generalization.
- At least one wrapper generated by Legwork gets reused from the public cache
  on a second run — proves the caching mechanic actually saves LLM cost and
  re-execution risk, not just the theory of it.
- **v1 scope boundary, stated plainly:** smoke-test fixtures (Next Steps #2)
  are CPU-only/lightweight repos. Success for v1 does NOT include correctly
  resolving PyTorch/CUDA/GPU dependency conflicts — the motivating pain
  statement names that problem, but a plain venv/Docker run (Approach A)
  doesn't solve it; only real sandbox orchestration (Approach B) can. This is
  a known, named gap, not an oversight: v1 proves the synthesis loop works;
  the hardest instance of the original pain point is Approach B's job.
- A repo whose README doesn't contain enough install/run information to
  locate an entrypoint produces a clear "insufficient information" failure
  message, not a retry loop burning attempts against a wrapper that can
  never succeed.
- **Explicit caveat (Outside Voice review):** passing the 3-5 hand-picked
  smoke-test fixtures does NOT itself demonstrate success on an arbitrary,
  never-seen repo — the two are different claims. The fixture set is a
  regression gate for the cache (did a change break a known-good wrapper);
  it is not evidence the synthesizer generalizes. The validation spike
  (Next Steps #1) and the live unscripted demo itself are what actually
  test generalization — not the fixture set.
- A target repo that requires its own credentials to run (gated Hugging
  Face models, API-backed demos) fails with a clear, correctly-labeled
  `CredentialRequiredError` — distinct from `InsufficientReadmeError` — and
  is explicitly unsupported in v1, not silently mishandled.

## Distribution Plan

- GitHub repo `AwesomeAI/legwork` is the primary distribution channel.
- Ship as an installable CLI via **uv/uvx** — `uvx legwork <repo-url>` needs
  zero install step, or `uv tool install legwork` for a persistent command.
  Chosen over pip at eng review: matches "lightweight, zero friction" from
  the original pitch, isolated per-tool environment avoids Legwork's own
  install inheriting the dependency-conflict problem it exists to solve for
  target repos. (Eng review, 2026-09-22.)
- GitHub Actions runs the smoke-test suite against every PR-proposed wrapper
  before it's eligible to enter the public cache. Free-tier runners are
  sufficient for v1 because smoke-test fixtures are scoped to CPU-only/
  lightweight repos (see Success Criteria). A GPU-heavy repo that can't pass
  the automated smoke test simply doesn't enter the v1 cache — there is no
  alternate "manually verified" tier in v1 (see Decided section); a fallback
  tier for GPU-heavy wrappers is Approach B's problem, not v1's.
- Each cache entry carries a manifest with these fields, stated completely
  here (this is the one place the schema is defined): source repo URL,
  commit SHA at synthesis time, synthesis date, wrapper language, source
  repo's license (redistribution-risk disclosure, per Constraints), the
  LLM model/version used for synthesis (provenance, per Outside Voice
  eng-review pass 2), and the smoke-test result. This is the minimum needed to know when a cached
  wrapper is stale and should be resynthesized against a new commit — the
  actual mechanism for "cache per repo-version" from the Cross-Model
  Perspective section. **Staleness trigger (Outside Voice, eng-review pass
  2):** checked on next contribution attempt only, no polling — when
  someone next runs Legwork against a repo already in the cache, the CLI
  compares the cached SHA to the repo's current SHA and flags "stale" on
  mismatch (doesn't force resynthesis, just surfaces it). No live polling
  infrastructure, keeping premise #3's "no hosted service" intact. A repo
  nobody re-runs Legwork against stays silently stale indefinitely — a
  known v1 limitation, not a silent gap.
- **Manifest also records the LLM model/version used for synthesis**
  (Outside Voice, eng-review pass 2) — closes a provenance gap: if a bad
  cached wrapper surfaces later, this is what correlates it back to the
  model/version that generated it, telling you whether to distrust one
  entry or the whole cache.
- **License check covers both signals (Outside Voice, eng-review pass 2):**
  the source-repo license flag (GPL/AGPL/none, as already decided) stays,
  AND the smoke-test step adds a substring-match check for the generated
  wrapper containing long verbatim copies of the source README/source
  files. The license flag is a weak, conservative signal (subprocess
  invocation typically doesn't itself trigger copyleft obligations); the
  verbatim-copy check targets the more concrete actual derivative-work
  risk — the codegen step copying source content into the wrapper — which
  neither prior pass checked.
- **License policy (Outside Voice review closed this gap):** a copyleft
  (GPL/AGPL) or missing-license source repo gets a visible flag in the
  manifest AND a warning line in the PR description, so the human merging
  the PR actually sees it and decides — it does not block cache entry
  automatically. This makes the license field an actual disclosure step
  (per Constraints) rather than silent, unread metadata.
- README leads with the live/unscripted demo, not a feature list — matches
  the "prove it, don't pitch it" positioning from the cross-model review.

   a local output directory; opening the PR to contribute it is a manual
   step for v1 (no auto-PR bot). A bad entry reverts with a plain
   `git revert` on its files — no separate invalidation tooling.
4. Record the first unscripted demo (a repo that trended that same morning,
   never seen before) as the README's opening proof — and disclose the
   prompt-injection risk plainly in that same README (see Decided section).
   Consider using the malicious `ai-data-extractor` case (with attribution
   and care about not amplifying it) as a companion "here's exactly why the
   obfuscation scanner exists" note — a real example lands harder than an
   abstract warning.
5. Run `/plan-eng-review` next to lock architecture (Python packaging
   choice, sandbox mechanism for v1, exact manifest schema, obfuscation
   scanner's specific heuristics) before writing code.

## What Already Exists (and why v1 doesn't just wire it together)

- **`mcp-gateway-registry`** — dynamic semantic tool discovery + routing, off the shelf. Not used in v1 because v1 has no router yet (Approach B); when it lands, this is the reuse target, not a rebuild.
- **E2B / Daytona / `kindling-mcp`** — mature ephemeral sandbox orchestration (Firecracker microVMs). Not used in v1 because v1's two-sequential-container approach is sufficient for a single-user local CLI; real orchestration is Approach B's job when multi-tenant/hosted use cases exist.
- **`cnoe-io/openapi-mcp-codegen`, ReadMe.com's MCP generator** — auto-generate MCP servers, but only from a *structured OpenAPI spec*. Cannot be reused for Legwork's core problem (synthesizing from unstructured README prose, per premise #2) — this is precisely the gap nothing in the landscape fills.
- **`vndee/llm-sandbox`** — evaluated for T5 (2026-09-22), rejected for this environment: its only backends (Docker, Kubernetes, Podman, Micromamba) all need an external runtime, and none were available on the dev machine — confirmed by trying each. Not a mark against the library, just a real result. Built on macOS's native `sandbox-exec` instead; worth re-evaluating once a container runtime is actually available (Approach B, portability).

## Worktree Parallelization Strategy

Sequential implementation, no parallelization opportunity — greenfield repo,
single core loop (Repo Fetcher → README Parser → Entrypoint Locator →
Codegen → Sandbox Runner → Cache Writer) where each component depends on
the previous one's output. Fewer than 2 independent workstreams exist yet.
