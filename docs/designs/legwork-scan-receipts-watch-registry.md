## Problem Statement

`find_tools` searches GitHub and Legwork's own cache of 47 reviewed tools, and nothing else. A repo that already ships its own MCP server is only labelled as such. The maintainer asked: "why not also check mcpserver and other famous or well known websites or public domains", and what other features are worth adding.

The measured bottleneck is not features. Legwork has 21 releases, 5 stars and 28 unique repo visitors in two weeks. People are not finding it, and those who do need a model key for anything outside the 47 cached tools.

## What Makes This Cool

Legwork's pre-install scan caught two byte-identical droppers in one week's ten most-starred new AI repos. Today that scan only runs when someone installs a tool. This design turns it into something people can see and try:

- Every week, CI scans the newest most-starred AI repos and publishes a receipt for each: the exact commit, what was checked, and the file and pattern found, if any.
- `legwork scan owner/repo` prints the same receipt in about ten seconds, with no model key and nothing installed into an AI client.
- Anyone can ask for a scan by opening an issue. CI replies with the receipt.

Then the registry: Legwork runs a server's own published package inside its sandbox, with no model-written wrapper, so no model key.

## Constraints

- No always-on infrastructure. CI and static hosting only.
- The scan needs no model key and runs none of the scanned repo's code.
- A receipt never says a repo is safe. A clean result says no covered patterns were found in the files checked, and names what the scan does not cover (Python and JavaScript/TypeScript source only; nothing an installer downloads later).
- The scan has flagged honest code before (lodash, for a vendored 2009 debugging script). Any public listing carries that risk.
- Hosted remote MCP servers are out of scope: nothing runs locally, so there is nothing to sandbox.
- Legwork gives tools no environment variables and no network by default. Passing a secret to a tool is not part of this design.
- Every PyPI release still needs the maintainer's explicit yes.

## Premises

1. Finding Legwork is the bottleneck, not features. A feature earns its place if it brings visitors or makes the first try work without a model key. Agreed.
2. The registry adds up to about 550 key-free tools; the real number is unknown. Measured: of about 15,000 servers in the official registry, 89% are hosted remote servers, 1,543 (10%) are local npm or PyPI stdio packages, 551 of those declare no environment variables and 916 declare a secret or required key. Declaring no variables does not prove a server runs in the sandbox with no network. Revised after the second opinion: the registry work starts by measuring.
3. Servers that need a key or the internet are a separate, later design. Agreed.
4. The watch can run on what exists: the scan is static, takes about a second per repo, needs no model key, and CI already runs weekly. Agreed.
5. Naming a repo is the watch's main risk. A listing shows the file and the pattern, makes no claim about intent, and has a way to contest it. A repo is marked "blocked" only when Legwork would refuse to install that commit. Agreed, with the blocking rule made exact after review (it was first worded as "only strong patterns").
6. Order: the watch first, then the registry. Agreed. This reverses the order the maintainer first picked.

Landscape: two young projects wrap MCP servers in virtual machines (declaw mcp-sandbox, nilbox). No recurring public feed of malicious trending repos was found. Research counts about 6 million suspected fake GitHub stars across 18,617 repos, and a campaign named FakeGit used about 7,600 malicious repos, more than 1,400 posing as AI tools, agents or MCP servers.

## Cross-Model Perspective

Codex, reading a summary cold:

- Coolest version: commit-level safety receipts. A page and JSON feed keyed to each repo's exact commit, with the scanner version, the file types covered, and the finding's file, line and pattern. `legwork scan` shows the same receipt and `find_tools` surfaces it. A clean result says only that no covered patterns were found. Adopted.

## Approaches Considered

- A. Smallest slice: the scan command and a weekly Markdown report in the repo. Not chosen alone: a Markdown file gets few readers and has no feed. It is stage 1 of the chosen approach.
- B. Receipts, then registry: chosen.
- C. Scan by request through GitHub issues: chosen as an addition, after the receipts exist.

## Recommended Approach

B plus C, in stages. Each stage is useful by itself and ships separately. Stage 3 from the first draft (receipts in `find_tools`) is deferred, and registry installs get their own design; both are explained below.

**The receipt.** One format serves the command, the watch and scan by request.

- The verdict uses the same rule `install_tool` uses today, applied file by file: a file blocks when it has a strong pattern, or two or more distinct weaker patterns. So a receipt and an install never disagree.
- There are five verdicts:
  - "blocked: Legwork would refuse to install this commit"
  - "not blocked: N weaker patterns noted" (findings exist, but no file meets the blocking rule)
  - "no covered patterns found in N analysed files"
  - "nothing this scan covers" (no Python, JavaScript or TypeScript source)
  - "scan could not complete", with the reason (clone failed, repo too large)
- N counts only files the scanner analysed. Files it skipped are counted separately and listed with the reason: a Python file that does not parse, or a JavaScript file over 5 MB. A skipped file is never counted as clean. This needs a new scanner entry point that returns a result per file; `scan_repo` returns only findings today.
- Every string that comes from the scanned repo (its name, file paths) is escaped for where it is shown: HTML and XML escaping on the page and in the feed; a code span with mentions and links neutralised in an issue comment; control characters stripped in terminal output.

**Stage 1: `legwork scan owner/repo [--commit SHA]`.** Shallow-clone with the existing fetcher, run the scan, print the receipt: repo, full commit SHA, Legwork version, files analysed and skipped by type, each finding's file, line and pattern, the verdict, and what the scan does not cover. `--json` prints the same as data. Exit code 0 for the three not-blocked verdicts, 3 for blocked, 1 for "could not complete". Exit code 2 is not used, because the CLI and argparse already return 2 for a usage error. Workflows read the verdict from `--json`, never from the exit code. `--commit` takes a full commit SHA and is passed to the fetcher's existing commit argument; without it the command scans the default branch as it is. A rescan of a held or contested repo uses `--commit`, so it checks the same code.

**Stage 2: the weekly watch.** A scheduled workflow selects the 50 most-starred AI repos created in the previous seven days, using the same GitHub search the September trial used. It reads each repo's size from the GitHub API and skips any over 200 MB with the "could not complete" verdict. It scans each at its current commit and writes one JSON receipt per repo and commit.

Unreviewed receipts are never in the public repo. A pull request on a public repo shows its files to anyone and keeps showing them, so the watch runs in a private repo that holds only the workflow and the receipts. It opens its pull request there. When the maintainer merges it, a second step pushes the reviewed receipts to the public repo, where the page and feed are built and published with GitHub Pages. That push needs one deploy key that can write to the public repo's pages branch and nothing else.

The maintainer reviews the private pull request each week. For each "blocked" receipt the choices are:
- Publish it as it is.
- Hold it, because the flagged code looks honest. A held receipt is left out of that week's page, and the page says how many are held without naming them.

A hold ends within 14 days, in one of four ways:
- The scanner is fixed. The repo is rescanned at the same commit and the new receipt is published with its scanner version.
- The scanner is left as it is, because the pattern really is in the file and the code is still honest (lodash is the example). The receipt is published with a maintainer note: the pattern is present, the maintainer read the file, and what the code is for.
- On a second reading the maintainer lifts the hold and the original receipt is published.
- The repo or commit is gone. The receipt is published marked as gone.

So every scanned repo gets a published receipt, that week or within 14 days of it.

Each blocked listing links to an issue template for contesting it. The maintainer reads the flagged file again and decides. If the "blocked" was wrong, the receipt stays on the page marked as withdrawn, with the reason and the date; where the scanner can be fixed, it is, and the repo is rescanned at the same commit. If the "blocked" stands, the owner's reply is linked from the listing. A published receipt is never deleted: a withdrawn one stays as a record, marked.

**Stage 3: scan by request.** An issue template, "Scan request", takes one repo name. A workflow:
- validates the name against a strict pattern and never passes issue text to a shell;
- counts the requester's scan-request issues in the last 24 hours through the GitHub API and refuses a fourth;
- reads the repo's size from the API and refuses above 200 MB;
- runs only the static scan, and holds only permission to write to issues.

What the requester sees:
- A not-blocked verdict: the receipt is posted and the issue closed. The request takes a repo name only, never a commit.
- A "blocked" verdict: the workflow replies with the commit it scanned and this wording: the scan found patterns Legwork blocks on; that is a pattern match and not a judgment about the repo; the details follow once the maintainer has read the flagged file. The reply carries the contest link and labels the issue. This reply does tell a reader that the verdict was "blocked", before any review. That is accepted, because anyone can run `legwork scan` on the same repo and get the same verdict, and the reply says only what the scan says. The file and pattern are what wait for review. The maintainer reruns the scan at that commit, reads the file, and posts the receipt, with a maintainer note when the code is honest, as in the hold path.
- A bad name, a missing or private repo, a repo over the size limit, or a fourth request in a day: a reply saying which, and the issue closed.
- A scan error: a reply with the kind of error, and the issue left open with a label.

Requested receipts stay in their issues. They are not added to the page or feed in this design.

**Stage 4: measure the registry.** A script takes all of the roughly 551 local npm and PyPI packages that declare no environment variables, not a sample. It runs on throwaway Linux CI runners with Node installed, never on the maintainer's Mac. For each package it:
1. downloads and unpacks the published package and runs the pre-install scan on it; a package the scan blocks is counted as "blocked by the scan" and not installed;
2. installs it in the sandbox with network on;
3. starts it with network off and asks it to list its tools;
4. calls each tool once, with sample arguments built from the tool's input schema (a short string, the number 1, a small fixture file for a path);
5. counts connection attempts to any address that is not the machine itself.

Legwork's own record of blocked network attempts cannot do step 5 here: on Linux it works only for a server started by Python and called through the hub, and most of these servers start with Node. So the measurement runs each server under `strace`, following child processes, and counts its `connect` calls during start, tool listing and tool calls. This is tooling for the measurement, not a change to Legwork.

It reports five counts:
- blocked by the scan;
- failed to install or start;
- started, but no tool could be called with sample arguments;
- at least one tool was called, and every call failed or tried the network;
- at least one tool call returned a result that is not an error, with no network attempt at any point.

Only the last group counts as working offline.

Decision rule, by count and not by share: 100 or more servers working offline justifies designing registry installs, because that is twice the 47 tools the cache holds today. Fewer than 50 stops the registry work, and the existing "already ships its own MCP server" label stays as it is. Between 50 and 100, the maintainer decides. Either way the numbers are published.

**Deferred: receipts in `find_tools`.** Dropped from this design. Receipts will exist for about 50 week-old repos a week, each at one commit, while `find_tools` returns six established repos, so a match would almost never appear. Revisit when the watch and scan by request have produced enough receipts to measure how often a search result has one. A later design must also decide the wording, so a clean receipt cannot read as an endorsement, and must keep showing an earlier "blocked" after the repo pushes a new commit.

**Separate design: registry installs.** If stage 4 passes, registry installs get their own design. It must answer what stage 4 leaves open: what the pre-install scan checks when the thing installed is a published package and not a repo; how a stranger's own tool names and descriptions are shown to the user's AI, since no Legwork-written wrapper stands in between; how the version is pinned; and the Node requirement.

## Open Questions

1. Is a private repo plus one deploy key acceptable as the price of keeping unreviewed receipts out of public view? The alternative is a public pull request, with the design saying plainly that receipts are public before review.
2. Is 50 repos a week the right size? The control run in the success criteria will show how many "blocked" verdicts a week to expect.

## Success Criteria

- Stage 1: in CI on macOS and Linux, `legwork scan` gives a "blocked" receipt for the malware fixture and a not-blocked receipt for a known-clean repo, and a test with a hostile file name shows it escaped in terminal, JSON, HTML and issue-comment output.
- Before the first public run: a control run over the watch's own population, the same search for each of the past eight weeks at 50 repos a week (400 repos). The maintainer reads every "blocked" file and records how many are honest code. This sets the expected rate; the earlier 1-in-150 figure came from popular, older repos, which the watch does not scan.
- Stage 2: a wrong "blocked" means one where the maintainer, reading the flagged file at pull-request review or after a contest, finds the flagged code hides nothing. The criterion is that no published "blocked" is marked withdrawn in the first four weeks. Holding a receipt at review does not count against it; that is the review working.
- Discovery: unique repo visitors per two weeks rise from 28 to 100 within four weeks of the watch going public, measured in GitHub's traffic page. This depends on the weekly posting described in the Distribution Plan.
- Stage 4: the five counts, published, whichever way they come out.

## Distribution Plan

- `legwork scan` ships in the next PyPI release of `legwork-mcp`, through the existing tag-and-publish workflow.
- The watch page and feed are built by a scheduled GitHub Actions workflow and served by GitHub Pages. Nothing to host.
- Scan by request runs in GitHub Actions on this repo's issues.
- Registry installs, if designed and built, ship in a later PyPI release.

How a weekly run reaches a reader:
- The README links to the watch page next to the malware result, and the article gets a line pointing to it.
- The page's header says in two sentences what Legwork is and gives the install command and the `legwork scan` command, so a visitor who came for the list can try the scan.
- Each week the maintainer posts the result where the article was shared (r/mcp, LinkedIn, X): how many repos were scanned and how many were blocked. The post gives counts and links to the page. It names a repo only under the rule below.
- A "blocked" verdict says a pattern is present, not that a repo is malicious. The maintainer reports a repo to GitHub only after reading the flagged file and judging it a hidden payload. That judgment is recorded in a separate log, not in the receipt. A post may name a reported repo, and says the report is the maintainer's own judgment after reading the file, not the scan's verdict.
- The 100-visitor target depends on this weekly post. Without it, a new page and feed start with no readers.

### R2-1 — consistency (blocking)

**Problem**

> The weekly pull request is itself public. kumarganduri/legwork is a public repo (README badges, PyPI, the cache/ folder linked from the README), and a pull request on a public repo shows its files to anyone, and keeps showing them after it is closed or the branch is changed. So every receipt, including each "blocked" one that names a repo, is public the moment the workflow opens the pull request, before any review. The hold outcome says a held receipt is left out of the page and counted "without naming them", but the held receipt's file is in the pull request with the repo's name in it. The design also does not say how a receipt is held (removed from the branch, moved to a folder). Naming a repo wrongly is the design's stated main risk, and this review step is its guard.

**Remedy**

> Decide where unreviewed receipts live so that they are not public: for example the watch runs in a private repo and only reviewed receipts are pushed to the public one. A workflow artifact or log on the public repo does not work either, since both are readable by others. Or state plainly that the pull request is public, drop the claim that nothing is public before review, and say why that is acceptable for a wrong "blocked". Either way, state the mechanics of holding one receipt.

### R2-2 — consistency (blocking)

**Problem**

> The "held" reply tells everyone the verdict. In stage 3 every other outcome has its own reply: a not-blocked verdict posts the receipt, and a bad name, missing repo, size limit, rate limit or scan error each say which. Only a "blocked" produces "the scan finished and the result is held for the maintainer", on a public issue that names the repo. So a requester aiming at someone else's repo gets a public "blocked" signal with no review, no file and pattern, no wording limits and no contest link, which is what the sentence "a blocked is never posted without that review" is meant to prevent. Two things the path needs are also missing: where the held receipt is kept between the workflow and the maintainer (the workflow holds only issue-write permission and keeps no state, and its logs and artifacts on a public repo are readable by others), and what the maintainer posts when the flagged file turns out to be honest code.

**Remedy**

> Choose one: make the first reply the same for every finished scan so that it reveals nothing, with the receipt following after review; or accept that the held reply discloses a "blocked", say so, and give that reply the wording limits and contest link. State where the held receipt is stored or that the maintainer reruns the scan locally, and state the outcome for a flagged file that is honest code (for example the same hold, fix and rescan path as the watch).

### R2-3 — feasibility (blocking)

**Problem**

> Stage 1 no longer has a way to scan a named commit, and the hold path needs one. The first draft's command was `legwork scan owner/repo[@ref]`; it is now `legwork scan owner/repo`, which scans the default branch as it is at that moment. Stage 2 says a held repo "is rescanned at the same commit" after the scanner is fixed, and workflows read the verdict from `legwork scan --json`. By the time the scanner is fixed, a week-old repo has usually moved on, so the command as specified would produce a receipt for a different commit. legwork/repo_fetcher.py already supports this (clone_repo's commit argument takes a full SHA or a tag), but the design does not expose it.

**Remedy**

> Add a commit input to the command (for example `--commit SHA`, passed to the fetcher's existing commit argument, which is simpler than parsing @ref), or state that the watch workflow calls the scanner entry point directly with a commit and does not go through the command. Say whether the scan-request pattern in stage 3 accepts a commit.

### R2-4 — completeness (blocking)

**Problem**

> The hold path has one ending, a scanner fix, and the design's own example shows that ending does not always happen. The Constraints cite lodash as honest code the scan flagged; the README says the scan still blocks lodash today, because the file really does run eval(unescape(...)), which is the strong pattern js-eval-of-decoded-string in legwork/obfuscation_scanner.py. So for a lodash-like repo the maintainer holds the receipt, the scanner is not changed, and the receipt stays held with no end. That contradicts the next sentence, "every scanned repo gets a published receipt, either that week or after a held one is resolved". The path also has no answer when the commit can no longer be fetched (the repo was deleted, taken down by GitHub, or force-pushed), when the maintainer on a closer read decides the code is not honest after all, or for how long a receipt may stay held.

**Remedy**

> List every way a hold ends and what the page shows for each: the scanner is fixed and the repo rescanned; the scanner is left as it is and the receipt is published with a maintainer note, or stays unpublished for good; the hold is lifted and the original receipt is published; the commit is gone. Then reword the "every scanned repo gets a published receipt" promise to match, and give a time limit or say there is none.

### R2-5 — consistency (blocking)

**Problem**

> The stage 2 success criterion counts withdrawals, but the design has no withdrawal and forbids removing a receipt. Stage 2 says "a published receipt is never deleted", and the only response to a contest is a rescan at the repo's current commit shown beside the old receipt. The criterion defines a wrong "blocked" as one where the maintainer, after a contest, finds the flagged code hides nothing. In that case nothing in the design changes the published listing: the old receipt stays "blocked", and the rescan gives the same verdict unless the scanner or the repo's code changed. So an owner of honest code who contests gets no correction, and the criterion measures an event that cannot occur. Open Question 1 asks who has the last word, but the criterion already makes the maintainer the judge; leaving the behavior as an open question does not supply it.

**Remedy**

> Define what happens to a published "blocked" that the maintainer finds wrong: for example the receipt stays on the page marked as withdrawn with the reason, the scanner is fixed and the repo rescanned at the same commit as in the hold path. Say how that fits "never deleted", state that the maintainer decides (or who does), and narrow Open Question 1 to what is still undecided.

### R2-6 — feasibility (blocking)

**Problem**

> On Linux, where stage 4 must run, that record does not exist for most of the packages being measured. legwork/seccomp_notify.py says a served tool without network on Linux fails its connections "with nothing recorded anywhere" unless the seccomp listener is installed, and that the listener needs "a served command that starts with Python". wrap() returns None when the command's name does not start with "python", and sandbox_runner.exec_serve then closes the socket with the comment "the hub sees the socket close and records nothing". A registry npm server starts with node or npx, and a PyPI server usually starts through its own console script, so neither is covered. The record is also written only around a tool call made through the hub (hub._record_denials), not for connections made while the server starts or lists its tools. As specified, step 5 would find no network attempts for every npm server and count it as "never tried the network", which is the one group the decision rule uses.

**Remedy**

> State how network attempts are detected for a server that is not started by Python and is not called through the hub. Options: extend the seccomp loader so that it can start any command and say that this is new work in stage 4; or detect attempts another way on the runner (for example run the server under strace for connect calls, or give it a network namespace with a logging resolver). Say that attempts during start and tool listing are counted too.

### R2-7 — feasibility (blocking)

**Problem**

> Stage 4 still counts as working offline a server that cannot do its job without the network. The new method calls only "each tool that needs no arguments" and then looks for network attempts. **Remedy**

> Report separately the servers where at least one tool call was made and returned a non-error result with no network attempt, and the servers where no tool could be called because every tool needs arguments. Count only the first group toward the 100 and 50 thresholds, or have the script call tools with sample arguments built from each tool's input schema and say so.

### Unresolved at the cap

1. R2-1 — consistency (blocking): The weekly pull request is itself public. kumarganduri/legwork is a public repo (README badges, PyPI, the cache/ folder linked from the README), and a pull request on a public repo shows its files to anyone, and keeps showing them after it is closed or the branch is changed. So every receipt, including each "blocked" one that names a repo, is public the moment the workflow opens the pull request, before any review. The hold outcome says a held receipt is left out of the page and counted "without naming them", but the held receipt's file is in the pull request with the repo's name in it. The design also does not say how a receipt is held (removed from the branch, moved to a folder). Naming a repo wrongly is the design's stated main risk, and this review step is its guard.
2. R2-2 — consistency (blocking): The "held" reply tells everyone the verdict. In stage 3 every other outcome has its own reply: a not-blocked verdict posts the receipt, and a bad name, missing repo, size limit, rate limit or scan error each say which. Only a "blocked" produces "the scan finished and the result is held for the maintainer", on a public issue that names the repo. So a requester aiming at someone else's repo gets a public "blocked" signal with no review, no file and pattern, no wording limits and no contest link, which is what the sentence "a blocked is never posted without that review" is meant to prevent. Two things the path needs are also missing: where the held receipt is kept between the workflow and the maintainer (the workflow holds only issue-write permission and keeps no state, and its logs and artifacts on a public repo are readable by others), and what the maintainer posts when the flagged file turns out to be honest code.
3. R2-3 — feasibility (blocking): Stage 1 no longer has a way to scan a named commit, and the hold path needs one. The first draft's command was `legwork scan owner/repo[@ref]`; it is now `legwork scan owner/repo`, which scans the default branch as it is at that moment. Stage 2 says a held repo "is rescanned at the same commit" after the scanner is fixed, and workflows read the verdict from `legwork scan --json`. By the time the scanner is fixed, a week-old repo has usually moved on, so the command as specified would produce a receipt for a different commit. legwork/repo_fetcher.py already supports this (clone_repo's commit argument takes a full SHA or a tag), but the design does not expose it.
4. R2-4 — completeness (blocking): The hold path has one ending, a scanner fix, and the design's own example shows that ending does not always happen. The Constraints cite lodash as honest code the scan flagged; the README says the scan still blocks lodash today, because the file really does run eval(unescape(...)), which is the strong pattern js-eval-of-decoded-string in legwork/obfuscation_scanner.py. So for a lodash-like repo the maintainer holds the receipt, the scanner is not changed, and the receipt stays held with no end. That contradicts the next sentence, "every scanned repo gets a published receipt, either that week or after a held one is resolved". The path also has no answer when the commit can no longer be fetched (the repo was deleted, taken down by GitHub, or force-pushed), when the maintainer on a closer read decides the code is not honest after all, or for how long a receipt may stay held.
5. R2-5 — consistency (blocking): The stage 2 success criterion counts withdrawals, but the design has no withdrawal and forbids removing a receipt. Stage 2 says "a published receipt is never deleted", and the only response to a contest is a rescan at the repo's current commit shown beside the old receipt. The criterion defines a wrong "blocked" as one where the maintainer, after a contest, finds the flagged code hides nothing. In that case nothing in the design changes the published listing: the old receipt stays "blocked", and the rescan gives the same verdict unless the scanner or the repo's code changed. So an owner of honest code who contests gets no correction, and the criterion measures an event that cannot occur. Open Question 1 asks who has the last word, but the criterion already makes the maintainer the judge; leaving the behavior as an open question does not supply it.
6. R2-6 — feasibility (blocking): On Linux, where stage 4 must run, that record does not exist for most of the packages being measured. legwork/seccomp_notify.py says a served tool without network on Linux fails its connections "with nothing recorded anywhere" unless the seccomp listener is installed, and that the listener needs "a served command that starts with Python". wrap() returns None when the command's name does not start with "python", and sandbox_runner.exec_serve then closes the socket with the comment "the hub sees the socket close and records nothing". A registry npm server starts with node or npx, and a PyPI server usually starts through its own console script, so neither is covered. The record is also written only around a tool call made through the hub (hub._record_denials), not for connections made while the server starts or lists its tools. As specified, step 5 would find no network attempts for every npm server and count it as "never tried the network", which is the one group the decision rule uses.
7. R2-7 — feasibility (blocking): Stage 4 still counts as working offline a server that cannot do its job without the network. The new method calls only "each tool that needs no arguments" and then looks for network attempts. Most MCP tools take arguments (a query, a URL, a path), so for a typical server no tool is called at all, nothing can try the network, and the server lands in "started, listed tools and never tried the network". That is the same gap round 1 raised: listing tools needs no network, including for a server whose every tool calls a web service. The decision to design registry installs rests on this count.
8. R2-8 — consistency (blocking): Reporting a repo to GitHub and saying so in public is a claim about intent, which the design says a listing never makes. Premise 5 limits a listing to the file and the pattern with "no claim about intent", stage 3 repeats those wording limits, and the Constraints note that the scan has flagged honest code. A "blocked" verdict means only that a pattern is present; the pull-request review holds back what looks like honest code but does not require the maintainer to judge the rest malicious. Yet the Distribution Plan reports "each blocked repo" to GitHub and announces it weekly on r/mcp, LinkedIn and X. The plan also does not say whether those posts name the blocked repos.
